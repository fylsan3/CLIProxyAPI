# 冷却衔接 A：实现记录与待集中验收

本轮保留 CPA 账号选择、重试配置和 ResetQuota 算法；不套用 Claude Code 的重试次数或运行时声明，不改变手改的 12 个请求头。功能测试继续暂停，不部署生产，不调用真实账号。

## 实现

1. worker 从原生错误提取 RetryAfter、凭据级限流和瞬时限流分类，以私有控制回执送回中央；用绝对时间表达等待期限，减少中转耗时导致的重复计时。中央 projectHTTPError 恢复原生调度器认识的接口。旧 worker 仅兼容其明确返回的 Retry-After 秒/日期和 Retry-After-Ms，不猜测账号级分类。
2. 私有回执只走容器—broker—中央，在客户入站和客户响应边界过滤；上游返回正文、公开 Retry-After 及用户模型头不因回执而改写。仍是两层 CPA 管理器，并非把它们合并成单一状态机。
3. 清除先交给绑定容器，使用原生 ResetQuota 并确认保存成功；中央收到成功回执后才调用自身 ResetQuota。失败/中断/无回执不宣称双层清除成功。容器保存失败期间阻止新模型调用，可重试本地清除。
4. broker 对单账号采用已有 maintenance gate，账号正在处理模型请求时返回 busy，不中断回复、不阻塞其他账号；worker 的本地入口与清除也共用短互斥保护。保留原版对已停用、认证失败的保护，清除不代表账号已恢复授权。
5. 管理详情并列显示中央和容器每个模型的调度状态、预计恢复时间；不把中央已清除等同于容器一定可用。
6. 不接入重置卡消费接口；清除本地冷却不消耗卡、不请求上游、不增加余额。

## Claude Code 对比依据

官方更新记录：https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md 。核对的最新版本为 2.1.332。记录确认了对 Retry-After 的处理、小 429 等待使用指数退避下限，以及默认整次模型调用最多 14 次请求的调整。它不是我们多账号中央/容器的实现。此处只借鉴完整传递等待信息与清晰呈现状态，不声称复制其完整算法。
